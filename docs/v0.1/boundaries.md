# API and state boundaries

These classifications guide later consumers. REUSE calls an existing service;
WRAP places a presentation or orchestration boundary above it; EVOLVE changes a
versioned surface in its assigned phase; FREEZE preserves compatibility; DEFER
keeps a future surface out of the current implementation.

```text
Today: CLI and Home -> current services / Engines -> one project store
Planned: CLI and GUI -> shared Application Service Layer -> those same services
```

| Boundary and classification | Current entry points and callers | State, authority and platform | Future consumer and compatibility |
| --- | --- | --- | --- |
| CLI and Home · WRAP | [`cli.main`](../../src/corinthos/cli.py) dispatches console and module entry points. [`run_shell`](../../src/corinthos/app_shell.py) owns Home and `corinthos .`, routes project operations through CLI handlers and calls provider functions for explicit actions. | Presentation and convenience writes. | Bootstrap and Standard Engine · REUSE | [`initialize`, `adapter_manager`, `show_adapters`, `configure_adapter`](../../src/corinthos/bootstrap.py) support Home, CLI, Project Manager advice and Workflow. [`load_standard`](../../src/corinthos/standard.py) validates the YAML policy. | Project profile, managed instruction files and provider overrides. M1–M5 are mandatory. Future setup keeps policy digest binding and uses the same initializer. A status read should avoid bootstrap, provider discovery and database creation. |
| User state · EVOLVE | [`state_root`, `read_state`, `update_state`, `initialize`](../../src/corinthos/user_state.py) support installer, Home and the registry. | Version 1 global JSON with locked read-modify-write and atomic replacement. ## Data ownership

| Scope | Data and update rules |
| --- | --- |
| Per-user convenience | Windows `%LOCALAPPDATA%/Corinthos`, or POSIX `$XDG_STATE_HOME/corinthos` with `~/.local/state/corinthos` fallback. `config.json` v1, `providers.json` v1 and `recent-projects.json` v1 use bounded documents. Setup creates config and MRU; provider observations may be absent. The MRU stores absolute normalized paths and timestamps, up to 20. Logs and cache are operational convenience. |
| Per-user installation | `%LOCALAPPDATA%/Programs/Corinthos` owns the runtime, launcher, app, immutable resources and inventory. Pinned cache is under the global state directory. These locations carry no project authority. |
| Per-project operational | `<project>/.corinthos/bootstrap.json` binds Standard and initial choices; versioned `adapter-<provider>.json` stores project overrides. SQLite hosts draft, runtime, Validation and lifecycle state. Local artifacts retain exact evidence digests. |
| Per-project canonical | `<project>/.corinthos/state.db` contains immutable contract revisions, exact references, active pointers and audit history. Source changes and artifacts keep their own Git/filesystem identities. |

For an operation, resolution is explicit override, project operational choice
(or initial bootstrap choice), explicit per-user choice, then safe
autodiscovery. A project reset is an explicit autodiscovery selection.
Registry observations supply diagnostics only. Startup, setup and reinstall
must remain passive with respect to providers. An explicit refresh/capability
check or an operation that requires a provider may perform bounded probing.

Keep Windows paths, registry, PowerShell and launcher details at the OS
seams. Windows remains the desktop/distribution target; Windows and Ubuntu
remain Core/Workflow Standard CI targets. Future GUI and CLI operations
must have equivalent canonical effects through the shared facade.
